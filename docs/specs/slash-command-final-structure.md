# 최종 슬래시 커맨드 구조 v32.0

## 🎯 설계 원칙

1. **명확성**: 각 명령어의 목적이 즉시 이해됨
2. **분리**: 생성과 검증은 별개 활동
3. **일관성**: 예측 가능한 동작
4. **단순성**: 필요한 것만 유지

## 📊 최종 구조 (10개 명령어)

### 🔵 개발 워크플로우 (5개) - 순차적 진행
```
1. /기획    → 요구사항 정의, PRD 작성
2. /구현    → 코드 작성, 기능 개발
3. /테스트  → 테스트 케이스 작성 (TDD)
4. /검증    → 품질 확인, Theater Testing 검사
5. /배포    → 커밋, 푸시, 태깅
```

**워크플로우 예시:**
```bash
/기획 "사용자 인증 시스템"     # PRD 작성
/구현 "JWT 토큰 기반 구현"     # 코드 작성
/테스트 "인증 플로우"          # 테스트 작성
/검증                        # 품질 확인
/배포 "feat: JWT 인증 구현"    # 릴리즈
```

### 🟢 분석 도구 (3개) - 필요시 사용
```
6. /분석    → 현황 파악, 문제 분석
7. /찾기    → 코드/파일 검색
8. /보고    → 진행 상황 보고서
```

**사용 예시:**
```bash
/분석 "API 응답 시간 느림"     # 병목 분석
/찾기 "getUserData"           # 함수 검색
/보고 "주간"                  # 주간 보고서
```

### 🟡 특화 도구 (2개)
```
9. /연구         → 연구 프로젝트 관리 (통합)
10. /전체사이클   → 전체 워크플로우 자동 실행
```

## 🔄 통합 및 변경 사항

### ✅ 통합된 명령어
```bash
# /실험 → /연구의 서브커맨드로
/연구 experiment "RGCCA v2"

# /research, /research-simple → /연구로 통합
/연구 [서브커맨드]  # 자동으로 Python/Bash 선택
```

### ❌ 분리 유지 (중요!)
```bash
# /테스트와 /검증은 별개 유지
/테스트  # 테스트 "작성" (Creation)
/검증    # 테스트 "실행 및 품질 확인" (Validation)

# 이유:
# 1. TDD 워크플로우 명확성
# 2. 책임 분리 (SRP)
# 3. 사용자 의도 명확화
```

## 📋 /연구 서브커맨드 구조

```bash
/연구 init [이름] [설명]        # 프로젝트 시작
/연구 track [내용]             # 진행 기록
/연구 experiment [이름] [설명]  # 실험 시작 (구 /실험)
/연구 hypothesis [가설]         # 가설 설정
/연구 milestone [이름] [설명]   # 마일스톤
/연구 checkpoint [메모]         # 체크포인트
/연구 status                  # 현황 확인
/연구 list                    # 프로젝트 목록
/연구 search [키워드]          # 검색
/연구 backup                  # 백업
```

## 💡 사용자 경험 개선

### 1. 명확한 역할 구분
```
/테스트 = "테스트를 만든다"
/검증 = "테스트를 돌리고 확인한다"
```

### 2. 예측 가능한 동작
```
사용자: /테스트 로그인
결과: test_login.py 파일 생성 (항상)

사용자: /검증
결과: 모든 테스트 실행 + 품질 보고서 (항상)
```

### 3. 워크플로우 지원
```
TDD: /테스트 → /구현 → /검증
일반: /구현 → /테스트 → /검증
```
